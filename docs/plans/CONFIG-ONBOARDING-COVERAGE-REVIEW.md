# Provider Configuration Flow Coverage Review

Date: 2026-10-03. Status: design review conclusions and follow-up wiring requirements; does not change the G1 stage gate and does not authorize real outbound calls. Based on [PRD R02/R21/A26](../PRD.md), [configuration main path](../design/07-POOLS-AND-CONFIG.md), [execution and probe rules](../DESIGN.md), [T2 configuration/API/execution task cards](workstreams/02-config.md), [T2 Web task card](workstreams/04-web-pools.md), [T2 execution task card](workstreams/03-execution.md).

## Conclusions

The user-described "select provider → select service / capability type → enter API key and model → save and activate" matches the accepted configuration main path. The minimal single-provider configuration closed loop lands in AUTH-01, CFG-08, API-01, WEB-02 after G1; this stage's task cards require a real API / real database and one verified offer. The full provider / resource configuration experience is in WEB-03, and the second provider enters at MULTI-01. T1 only accepts the static configuration compilation rules and does not mean these services/UI are implemented.

The review decides two items:

1. **Complete the online credential verification semantics.** Currently PRD R02 requires verifying credentials, DESIGN §9 also includes "configuration validation/activation" in the onboarding route, and DESIGN §2/§5 already have a controlled-network probe entry point; but the current T2 cards do not define the user-triggered credential test operation, how the activation result represents credential "untested / passed / failed", or its billing and credential authority scope. Therefore "a wrong key is certain to be discovered only at the first business request" cannot yet be asserted; the correct statement is that current specifications do not promise it will be discovered before the first business request. This item is listed as a coverage gap to clarify before accepting the T2 configuration closed loop.
2. **Make service type a bounded catalogue selection while preserving the plan facts' original text.** ProviderDescriptor already registers field schema, capability profile, and executable capabilities, so the API/service capabilities and supported models the user selects should come from the server-side catalogue. The test descriptor's `planName` is an ordinary string and cannot represent that a production catalogue has already enforced this constraint. On the other hand, the provider's actual plan name is itself an account fact and must be preserved verbatim per console / order text with evidence timestamps; it is inadvisable to require compiling the provider's ever-changing plan display names into permanent enumerations. The catalogue should distinguish controlled selections such as a stable `serviceTypeId` / `modelId` from the evidence-verified `providerPlanName`, and the server then maps the latter to a supported preset.

## Implementation Constraints for Credential Testing

At implementation time, provide an explicit "test connection" action separate from save / activate. Save and activate still complete validation of local structure, credential reference existence, schema, metering facts, evidence version, and activation atomicity; a binding on which no network test has been executed shows "not yet tested" and must not fake connection success. When the test is clicked, it is initiated by an authorized administrative identity and uses the same binding, credential version, endpoint, and selected model as specified by the provider preset. Exemption from business metering is allowed only when the provider officially supports a dedicated authentication probe that is demonstrably non-billable and sufficient to prove the target capability; an ordinary models/list or health endpoint cannot prove model call permission/availability.

A minimal real inference request may deduct quota or incur costs; it must be clearly indicated and explicitly triggered within the scope of the user's existing test authorization for count/cost. It should reuse DESIGN §2/§5's controlled `system_probe` / Transport / permit and accounting paths; it is not a network side effect hidden inside Validate/Activate, nor is an ordinary public execute request accepted disguised as an internal administrative probe. Accounting, wrong credentials, no model permission, network failure, actual usage, and timeout/unknown are displayed separately; logs contain no key or request body. Only verified calling facts can lift the authentication block on the corresponding credential/binding; network reachability does not mean the model has permission or that usage is strictly free. When the provider offers no compliant probe capability, display "cannot be verified online / requires an approved minimal call", and the user chooses whether to perform a real test.

## T2 Wiring and Acceptance Ownership Recommendations

After G1, first implement the local and real-database safe paths for configuration/compilation/API; once RUN-01/02 deliver the corresponding Adapters and controlled Transport and the ledger probe port exists, then wire up the administrative credential probe API and UI. If the current write set / dependencies cannot accommodate that operation, Codex updates TASK-INDEX and registers a narrow probe API task with its explicit prerequisites, avoiding implicit network access in WEB-02 or API-01; until then WEB-02 must explicitly show that credential status has not been verified online. WEB-03 accepts the provider catalogue, service type/model controls, and probe status/actions; real outbound requests remain authorized and accepted under the existing RUN-05 test scope.

Minimal acceptance assertions:

- Correct credentials + unsupported model, wrong credentials, no probe permission, and timeout/connection error each display a distinct, repairable status; the test result is bound to the exact `bindingId/credentialRevision/modelId`, and changing the key or model immediately marks the old result stale.
- Testing is separated from saving, activation, and real business submission; without cost / count authorization, billable inference requests must not be sent. Each probe actually sent is at most one provider request, uses the same secure credential path, and does not auto-retry or redirect; reports real usage or unknown and records it in the ledger.
- The provider catalogue explicitly states the supported `serviceTypeId`, model set, protocols, and test method. Unknown service types may be stored as description drafts but cannot be activated for execution; plan display names entered by the user do not by themselves create new capabilities / upper bounds.
- Switching `serviceTypeId`, endpoint, model, account, or credential revision requires re-verifying compatibility; an existing activated version stays valid even when a new draft fails.

This delivery does not break the G1, IN-03 provider admittability, or real-test authorization boundaries. All new network tests remain explicit and accounted for, and "verification succeeded" is never treated as proof of quota.
