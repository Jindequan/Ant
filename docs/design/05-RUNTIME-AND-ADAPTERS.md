# Go Lifecycle, Provider Adapters, Streams, and Operations

Version: V0.7. For contracts see [contracts.go](contracts.go); for the execution chain see [Execution Algorithms](03-EXECUTION.md); for UI/API see [Communication Design](08-API-AND-EVENTS.md).

## 1. Configuration and Capability Catalogue

RuntimeConfig contains accounts, bindings, resources, offers, pools/members, grants, evidence, and RuntimeSettings. ProviderDescriptor is registered in code and provides JSON configuration/resource schemas and implemented domains/capabilities; the UI can configure different types, but a provider protocol cannot be auto-generated from arbitrary JSON. ConfigService holds the draft→validate→activate entry point, the Ledger performs atomic publishing, and a failed old activation is not overwritten by new configurations. Secrets only keep secretRef/revision.

Starting Settings: maxActiveOperations 128, writerQueue 512 / control reserved 128, readConnections 4, lease 30s, heartbeat 10s, sweep 5s, planningMaxRounds 3, commandBudget 50ms, busy 10ms; D04/D06 freeze these based on real inputs. maxAttempts/deadline are operation policies, fixed at first claim.

## 2. Adapter and Controlled HTTP

DomainPolicy.Normalize/Compile/Validate → Adapter.Encode → EncodedValidator → Transport.Prepare (resolve credentials early, copy the immutable wire body, digest) → Ledger.TryPrepare/Authorize → Transport.Dispatch. The persistent ExecutionPlan fixes provider type, endpoint, credential ref/revision, and adapter revision; Transport verifies that the encoded request's endpoint and credential ref match the plan verbatim, preventing an adapter from redirecting credentials to another target. The Adapter only has encoding/decode and evidence projection ports; no http.Client/SQL/secret resolution. requestDigest covers method/URL/non-secret headers/body and the credential injection rule (header/field/prefix); a permit additionally binds credentialRevision; secret values are not included. Transport alone resolves `CredentialRef+revision`, injects the specified header only immediately before actual sending, and never logs secrets.

The standard Go Transport may resend replayable requests on network errors of old connections, and `NewRequest` automatically sets `GetBody` for common bodies; see [net/http](https://pkg.go.dev/net/http). The current controlled client fixes HTTP/1.1, disables connection reuse, sets `GetBody=nil`, disables redirects (returns the raw 3xx), does not configure proxies, and does not enable provider retry SDKs; the response body has a caller-defined limit, header wait, and an overall timeout. Each permit executes `Do` exactly once, and on a brand-new connection, avoiding hidden replays after reusing a bad connection. HTTP/2 and connection pooling are not enabled.

Transport validates the final request before consuming the permit; after the local handle is atomically marked used, it calls the Ledger's persistent CAS, and only if the CAS succeeds does one HTTP send proceed. The handle binds runtime/attempt/owner/credentialRevision/digest; credentials exist only briefly in Transport memory, and request copies are cleaned up afterwards. Current unit tests cover local 3xx non-following, response size limits, HTTPS constraints, credentials not entering the digest, and handle non-reusability; SQLite integration tests use a local TLS server to verify that the permit row is already `consumed` when the request arrives, and verify that when a pool version change makes the CAS fail, the network request count is zero. Still needed: a counting fault server covering zero-byte writes, half-writes/received-but-unanswered, old-connection failures, and cancellation races. One permit does not mean provider exactly-once; a partial send failure defaults to unknown. Timeouts, 5xx, EOF, and context cancellation by themselves do not prove a safe retry or external termination.

DispatchPermit is encapsulated inside the transport/ledger collaboration; its fields cannot be constructed by deserializing from the API; a server-private handle table binds runtime/nonce/plan digest. First mark it once atomically locally, then in the consume-permit transaction CAS granted→consumed with final control/pool/owner checks; when the response is unclear, sending rights are not re-acquired. Prepare first, then authorization; no long computation or external evidence gathering is inserted between the final validation and the network.

`application.CandidateOperationExecutor` currently executes per candidate: quote → adapter encode → Transport prepare → ledger prepare/authorize → single dispatch → persist output → settle; after a prepare rejection it re-reads candidates with a new attempt identity and then tries subsequent offers. When a transport/decode failure occurs after the request has already obtained sending rights, it is not resent; the Ledger converges conservatively via the no-reliable-end-evidence path. The quote is only a planning precheck; TryPrepare remains the authoritative transaction for resource reservations. The executor receives domain planning, the adapter catalogue, guard evidence gathering, the ledger, and Transport via explicit interfaces; the current composition root has not yet registered production policies/adapters, nor mounted the Submit route, so it does not yet constitute a user-executable chain.

## 3. Persistent Output and Bounded Backpressure

response.Body → Adapter.Decoder → OutputWriter → Ledger.AppendOutput → StreamHub/operation_events. The first chunk and visible_output_at are in the same transaction and become visible only after commit; after the first segment is visible, automatically switching providers to stitch output is forbidden. The body is read in pages, and events only reference chunk ranges.

Starting values: 32KiB or 50ms chunking per stream, 128KiB ring buffer, 16MiB maximum retained body, 30s response/consumer idle; the writer merges across attempts into short transactions of at most 32 items / 256KiB / 25ms wait; each item is written only if its guard is legal, and a whole-database error rolls back the entire batch. Delivery happens after ACK, and control commands take priority. It is not one FULL transaction per token. Values are frozen by D04; first-segment/tail latency is measured, and claiming a first segment below 50ms based on 50ms batching is not allowed.

If a consumer is slow or leaves, detach the subscription; decoding continues saving/settling within limits; if the database is slow, backpressure applies to the network within a fixed buffer, and timeouts fail explicitly as unknown. When the body limit is reached, produce a partial and request a local stop; if external termination is unproven, keep the reservation. SSE reconnection reads saved events/chunks and does not resume the original network stream. Retaining metadataOnly must state which body content cannot be retrieved.

## 4. Go Context, Heartbeat, and Recovery

`runtime.ExecutionHost` has implemented process-level task capacity reservation: before submission, non-blockingly take one slot, returning Busy immediately when full; if Claim fails, call Release; on success, Start attaches a deadline task parented to the server root Context. Cancellation is first recorded as persistent intent by the Ledger, then Host.Cancel notifies the local task; shutdown stops accepting, cancels active tasks, and waits within the caller-specified time limit. The HTTP request Context is not passed into tasks. Task panics are isolated by the host and release local capacity; the panic value is not written to logs; the persistent ledger is still left to recovery sweeping to judge; the host does not infer provider termination and does not replace task settle. `MaxActive=0` uses the 128 default. `runtime.Supervisor` uses a fixed process-level loop, renewing leases in batches per namespace and reading the current runtime's persistent cancellation intents; when renewal is unauthorized or control reads fail, local tasks of that namespace are stopped; sweeping takes at most 100 items per batch. `ant-server` assembles the Host and Supervisor when the local test configuration service is enabled. Submit/Router are not yet wired to the Host, so no user submission currently enters this task loop.

Each operation ctx is created by the supervisor; deadline/persistent cancel can cancel provider reads; it does not derive from the browser's r.Context. Heartbeat and sweep are a fixed small number of supervisor goroutines, renewing in batches, with per-item owner/generation guards. Notification channels are not a reliable source of truth; periodic reads of persistent cancel/control are the fallback; multi-process control starts at batch 100 and 1s polling. Do not create a set of never-exiting tickers per task.

settle uses an independent bounded context, avoiding the inability to write facts after the business ctx is cancelled; storage failure explicitly reports not-persisted, retrying the ledger with the same attempt/reportId rather than the provider. The lease only judges local ownership; unknown external reservations are released by end evidence. The clock is controlled: backwards movement seals new permits, while what has already been sent is still accounted; database conditions use a consistent time policy.

## 5. Administration, Secrets, and Disposal

The first-version administrator bootstrap comes from a one-time local CLI action; session/token stores only hashes. Secrets use AES-GCM with a fresh random nonce per item and ref+revision as associated data; the master key file/system key service lives outside the database; file permissions 0600 / directory 0700, and the backup master key is managed separately. Do not invent your own password derivation algorithm; in the early stage, API tokens/bootstrap credentials only; no public registration/billing platform.

QueryAdmin is a read-only projection with on-demand observation refresh, verification, and repair; refresh networking runs outside transactions, using Transport/permits/accounting through verified system_probe plans; without an API, import only evidence with provenance. Unreliable observation watermarks are diagnostic only: no admission, no fabricated capacity, no automatic business retries.

Logs are structured and correlated by operation/attempt/account/binding/pool/offer/config, recording queue/lock/admission/call spans, without credentials or bodies. The metrics endpoint is restricted to admin permissions; pprof is not public by default, listening only for admin when tests need it. Deduplication identities and unknown evidence are not auto-deleted; body cleanup is decided by D05.

Backup reads a consistent SQLite snapshot covering ledger/configuration pools/events/reservations; secret keys are independent. Recovery must restore_guard to seal outbound calls, checking backup gaps and unknown executions; open only after authorized audit. Rolling back configuration produces a new activation version; balances and history are not rolled back.
