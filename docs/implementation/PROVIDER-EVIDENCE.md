## 2. DeepSeek API: verifiable dimensions and remaining gaps

Public billing separates input cache hits, input cache misses, and output; gifted balances are consumed before topped-up balances, and current prices also have peak/off-peak periods. The specific model/version, currency, price version, and corresponding periods must be frozen; the gift quota must not be treated as permanently free, nor may one choose on one's own to deduct only the gift quota. [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)

The balance endpoint `GET /user/balance` provides the available balance, currency, total, unexpired gift quota, and topped-up balance; the public example is not the user's balance. The documentation, in this evidence collection, does not provide an observation point/submission watermark usable for reconciliation; a read value can only become a candidate snapshot carrying its retrieval timestamp, and cannot yet prove concurrent consumption deltas. [Balance API](https://api-docs.deepseek.com/api/get-user-balance/)

`402 Insufficient Balance` proves that insufficient balance raises an error; from this one must not infer "stop immediately once the gift quota is exhausted", "independent budgets per key within an account", or "a zero-cost hard stop that never overspends". [Error codes](https://api-docs.deepseek.com/quick_start/error_codes/)

The Chat documentation defines `max_tokens` as the generation cap, states that input plus generation is bounded by the context, and gives finish_reason and usage details for input/cache/output/reasoning; the last SSE content chunk carries a non-empty finish_reason and the full usage, followed by `[DONE]`. Before formal adoption it must also be proven whether the selected model's reasoning is fully counted within the output cap, the enforceable upper bound over all encoded inputs, and erroneous usage. Do not carry over the old model's default cap. [Chat API](https://api-docs.deepseek.com/api/create-chat-completion/)

The official tokenizer documentation makes clear that offline computation is only an estimate and that API usage is the actual fact; therefore offline estimates must not be taken directly as the enforceable billing upper bound. [Token Usage](https://api-docs.deepseek.com/quick_start/token_usage/)

**Capabilities currently rejected:** the unverified account's initial capacity/gift quota expiry/billing authorization; a free-only hard stop is unproven; a full-dimension enforceableBound is unproven; server-side termination after disconnection or cancellation is unproven. A fully received termination with usage can serve as candidate evidence of a normal terminal state, but disconnection/timeout is not equivalent to external termination.

## 3. Alibaba Cloud: the Token Plan and free-tier model quotas are independent facts

The China-site Personal Edition FAQ states that Credits use a 30-day cycle starting from the subscription date, not calendar months, with no carryover; when the quota is exhausted it blocks and does not convert to pay-as-you-go, and separately purchased usage packages can then be deducted. The plan itself has no free gifted Tokens; model free quotas are independent. The console subscription page provides usage; the recommended concurrency is not a verifiable hard limit, and TPM/RPM are dynamically adjusted. Harness is accounted separately and may be post-paid; the first thin slice should exclude tools such as search. [Personal Edition FAQ](https://help.aliyun.com/zh/model-studio/token-plan-personal-faq)

**Regions/versions must not be merged:** the international-site blog describes 5-hour + 7-day rolling Credits with unified deduction for multimodal/tools, while the current China-site FAQ describes a 30-day cycle and an independent Harness; the international blog's examples and the cycle table on the same page should also not serve as capacity grounds for the user's plan. Preserve the source differences; do not infer which one is the version the user purchased, do not configure the 30-day cycle as fixed/month, and do not configure Credits as raw tokens. [International-site description](https://modelstudio.alibabacloud.com/intl/blog/model-studio-token-plan-individual/)

Official rules for the new-user model free quota: usually 1M per model, Beijing region only, independent across different models and snapshots; shared between the main account and RAM sub-accounts, with a validity of usually 90 days. For authenticated users with protection not enabled, exhaustion automatically converts to pay-as-you-go. With "stop upon exhaustion" enabled, exhaustion returns `403 AllocationQuota.FreeTierOnly`; configuration has an activation delay, and the official notice says billing may still occur during that period. A screenshot of the toggle must not be taken as taking effect immediately, "usually 1M" must not be treated as the initial balance, and new keys must not be allowed to multiply the quota. [Free quota rules](https://help.aliyun.com/zh/model-studio/new-free-quota)

The standard inference channel and the plan-specific Key/Base URL are not interchangeable. The current China-site Token Plan is `token-plan.cn-beijing.maas.aliyuncs.com` and Coding Plan is `coding.dashscope.aliyuncs.com`; the standard API recommends workspace domains. Choosing the standard API/free quota is not a silent switch of the user's plan but an alternative combination requiring the user's explicit confirmation. [Base URL](https://help.aliyun.com/zh/model-studio/base-url), [Regions and domains](https://help.aliyun.com/zh/model-studio/regions). On 2026-10-04 the Base URL documentation was re-checked: both plan endpoints are labeled "for interactive use by AI tools such as Claude Code and Codex only; must not be used for backend services", and a plan Key must be paired with the same plan's endpoint (mismatch returns 401) — Alibaba Cloud's Coding Plan, like the Token Plan, is explicitly excluded by this documentation from backend programmatic use.

The standard Chat API's `stream_options.include_usage` can provide usage in the final chunk; the specific model's thinking cap, cache, tool costs, and parameter semantics must be checked. The old Completions documentation even states that max_tokens may only truncate the returned content without affecting generation, so output parameters must not be applied across APIs as hard billing caps. [Chat API](https://help.aliyun.com/en/model-studio/qwen-api-via-openai-chat-completions), [Completions parameter description](https://help.aliyun.com/zh/model-studio/completions)

**Capabilities currently rejected:** Token Plan backend usage permission is unproven; the model free quota's remaining balance/expiry/protection effectiveness is not obtained; Credits' exact deduction, rounding, plan add-on packages, and observation watermark are not obtained; the selected model's full enforceable upper bound is unproven. The public blocking rules can support later account verification but do not yet support strict free admission.

## 6. Official product and protocol freshness increments (2026-10-05)

This pass only read official public pages; no account was queried, no plan settings were changed, and no model API was called.

- **DeepSeek model routing has a page conflict.** The current [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/) table still lists `deepseek-v4-pro` / V4-Pro-0813 as an independent model; the newer [2026-09-10 V4.1-Flash release notes](https://api-docs.deepseek.com/news/news260910/) say that from 2026-09-14 04:00 UTC, `deepseek-v4-pro` requests are temporarily routed to V4.1-Flash and billed at Flash prices until V4.1-Pro is released. Implementations must not take the static price row of the V4-Pro alias directly as a current independent pricing fact; using explicit `deepseek-flash` avoids treating that alias as a different model. Before deployment, the consistency of the routing and pricing pages must still be re-checked.
- **The DeepSeek finish-reason set has been extended.** The current [Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) lists, besides `stop`, `length`, and `content_filter`, also `insufficient_system_resource` and `aborted`. If the server returns complete and consistent usage, these two kinds of terminated responses should be handled as failure or unknown by a pure classification policy with the exact usage preserved; they must not be mistaken for success, nor may already-received settlement data be discarded because the finish reason is unrecognized. `max_tokens` is 1–384K, with defaults varying by thinking mode; the specific request policy must still verify the message upper bound together with the model context.
- **Alibaba Cloud output-cap semantics are clearly distinguished.** The current [OpenAI-compatible Chat API](https://help.aliyun.com/en/model-studio/qwen-api-via-openai-chat-completions) recommends that new integrations use `max_completion_tokens`, which limits the total output of chain of thought plus the visible answer; plain `max_tokens` is answer-only on many models, with chain of thought separately bounded by `thinking_budget`. The documentation also notes that the actual output count of `max_completion_tokens` may exceed the requested value by up to 10 tokens. The request policy must choose the field per specific model and leave enough headroom for the documented deviation; similar field names must not be taken as identical metering semantics.
- **The Alibaba Cloud new-user free quota page has a region wording conflict.** The [Free quota page](https://help.aliyun.com/en/model-studio/new-free-quota) says in one place that only Beijing is eligible, but its FAQ says elsewhere that the Beijing and Singapore regions may have quota. Continue item-by-item verification by exact region, service scope, and model; all regions must not be judged identical based only on the earlier part of the page, and "usually 1M" must not be written down as an account fact. The page still states a 90-day validity, merged deduction of input and output, account/RAM sharing, and minute-level refresh of quota data; Free Quota Only can return `403 AllocationQuota.FreeTierOnly` on exhaustion, and setting changes have an activation delay.

The impact of this re-verification on the generic codec is recorded in [Chat Completions adapter evidence](../evidence/WORK/CHAT-COMPLETIONS-ADAPTER/README.md): it now preserves the choice between `max_tokens` and `max_completion_tokens`, accepts the standard values of `reasoning_effort`, and hands known termination states to the provider policy for classification. This protocol extension does not constitute evidence of any production model policy, price registration, account authorization, or real request.
