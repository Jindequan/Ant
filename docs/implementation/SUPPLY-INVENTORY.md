## Business definition

1. **User:** the administrator who owns several provider accounts and needs to configure their plans/resources before enabling calls.
2. **Value:** save what an account owns, see its allowances and commercial rules, and choose the order in which compatible supplies should later be used.
3. **Objects:** provider identity; provider account; resource package (subscription, purchased credit, free allowance, pay-as-you-go); named resource declaration; versioned renewal/window rule; price; compatible supply pool with ordered package references. An account may have several packages; a package may have several resources; account-scoped limits automatically constrain every package on that account and are referenced once rather than copied. Removed package resources retain their identity as retired declarations and can be restored. Identifiers are generated, references use identifiers. Quantities and prices are canonical exact decimal strings, never floats. Inventory rule version is pinned independently of executable ConfigDocument v1.
4. **Loop:** choose provider/account → describe a package → configure its named allowances → save atomically → GET inventory → configure compatible pool and order → reopen/edit/archive/restore. Existing SQLite writer, authentication and executable ledger are implemented; this inventory model/API/UI and pool setup were unimplemented at design time and are now implemented with local verification recorded below. The next phase admits verified inventory into executable configuration; no such bridge is claimed here.
5. **Non-goals:** calls, credential collection, balance observation, automatic provider-plan synchronization, invented provider pricing, total balances across unlike units, visual redesign, replacement of the execution ledger.
6. **Commercial rules:** quantities are declared capacity, not available balance; cost is informational commercial configuration, not a charge. Subscriptions may renew; credits/free allowances may expire; pay-as-you-go has explicit configured spending limits. Each resource may have an independent reset window. Package price cadence and resource reset are distinct. Archive is reversible and removes that package from proposed pools. No refund or provider cancellation is performed.
7. **Acceptance:** Given an empty namespace, when an administrator supplies their provider/account and a subscription with two different allowance windows, then one save persists all objects and GET shows named allowances without raw IDs. Given that account, when they add a separately expiring credit package, then it shares the account but retains its own resources, expiry and price. Given compatible packages, when a pool order is saved, then GET returns the order. Given stale version/read-only/cross-namespace access, when writing, then the server rejects without overwriting stored data. Given a saved package, when archived/restored, then its identity and declarations survive while pool references are safe. Given a restart, then all saved inventory persists. Given quantities larger than JavaScript's safe integer, then their exact decimal representation survives UI/API/SQLite readback.

Value evidence is the user's explicit request and repeated rejection of the previous flow. Usability risk is tested with the real empty-state journey. Feasibility uses the existing serialized SQLite Store and auth middleware. Commercial risk is controlled by never claiming declarations as verified balances or creating provider charges.

## Page contracts and storage boundary

Keep Providers / Resources / Pools / Operations. Reuse established tokens and components; this corrects business structure, not visual identity.

**Resources:** unique question: what resources have I configured? Business: provider accounts and packages. Data: namespace inventory/version and package/resource definitions. First screen: named packages grouped by account, type, allowances, renewal/expiry, configured status. Main CTA: add a package. Secondary: edit/archive/restore, continue to pools. Entry: authenticated read/configure. Success: one API save followed by GET; package appears with its actual rules. Failure: inline field guidance or version-review/retry while preserving inputs. Leave: cancel/back restores inventory; navigation with unsaved inputs offers keep/discard. Permissions: read can inspect, configure can mutate, API rechecks grants. Setup is three steps: provider/account, package/commercial rules, resources; there is no apply-then-save-draft step. Internal IDs/precision/evidence references are absent from normal setup.

**Pools:** unique question: which configured supply should be used first? Business: proposed compatible package ordering. Data: pools and package/resource references from the same inventory version. First screen: pool name, declared capability, ordered supplies. Main CTA: create a pool (or save when editing one). Secondary: edit, move up/down, remove/undo. Entry: at least one configured package; empty points back to Resources. Success: atomic CAS save then GET ordered references. Failure: retained edits and explicit version review. Leave: cancel/back, dirty navigation guard. Permissions: read/configure as above. These are configuration pools; executable pool views remain separately identifiable.

Loading/empty/error/success/read-only/conflict states are required. Cold start requires provider selection, account/plan name and at least one allowance; credentials are optional because execution is subsequent. Provider choices are identity helpers, never an assertion that an adapter or plan is verified. Custom providers, metrics and capabilities are supported through data declarations; schema version and execution admission remain core-controlled.

Add SQLite migration v4 with one namespace-owned inventory record (version + document JSON). The additive Store capability uses existing snapshot reads/serialized writes. Every save validates a closed versioned document and typed references before entering a transaction, enforces expectedVersion inside it, and stores a principal/namespace-scoped command receipt plus audit in the same commit. Existing records are archived, not deleted; existing IDs/owner/provider identity cannot be repurposed. Existing executable ConfigDocument v1 and config_drafts remain untouched. No execution adapter, secret cipher, transport or master key is added. Inventory is available only in the existing business-enabled modes.

Verification must include meaningful graph/quantity/window tests, real SQLite CAS/idempotency/isolation/restart behavior, API permission/strict-body checks, Web journey/conflict/read-only cases, and desktop/390 real-stack screenshots.
