## 4. AI Real Request and Success Boundary Draft

Inputs must be exported sanitized from the chosen application, not invented as product examples. Record the calling application / workflow, business purpose, trusted namespace and authorized poolId, stable operationId, domain/capabilityProfile, real input content structure, model capability requirements, maxOutputTokens and other output constraints, whether tools / reasoning / cache are enabled, required affinity, allowMetered, maxAttempts/deadline policy, the stream consumption mode, and the business success judgment. Sensitive bodies are kept only in approved storage; reports keep sample references / summaries; credentials are registered only as ref/revision/mask and never enter documents or logs.

"accepted" means the server has taken over, not that the AI succeeded; receiving the first chunk is not complete success either. The success draft is: the designated business workflow obtains usable complete text, the provider termination evidence and the necessary usage projections are explainable, and the persisted final state and retention scope are queryable. Concrete content correctness is determined by the real application; "having text" must not substitute for the business standard. The succeeded terminal state is separate from the resource state: if counting is conservative or termination evidence is insufficient, queries still show usage pending verification / unreleased reservations, and termination proof is never fabricated.

The first real verification uses one account and one minimally authorized request, walking config GET read-back → verify/activate → submit → first-chunk/complete output → settlement → same-ID query/replay; then it verifies the two independent accounts' ordering and safe failover. Real concurrency / fault actions are bounded by the allowed budget and provider facts; damaging faults run against a local controlled fault provider, real providers are never deliberately made unreachable to incur charges, and simulated evidence is labeled separately.

## 6. Load and Backpressure Measurement Methods

Before measurement, freeze one run manifest: the actual application's sample source/date; accounts / resources / hotspots and their sharing distribution; request sizes, output tokens and bytes, long-task durations, event / stream speeds, and the success / rejection / fault mix; whether 20/s, the 50 long tasks, the historical volume, and the 2 hours are grouped or combined; warm-up scope/duration, effective sampling interval, quantile algorithm, repetition rounds, cost cap, and stop conditions. Unknown items are marked one by one; "typical" numbers are not filled in first. Differences between the production target and the local / near-production measurement environment are registered by CPU/memory/disk/OS/Go/SQLite/fsync mode/network TLS proxy/browser/process supervisor/parallel services.

Spans use single-host monotonic time to measure ANT intervals; UTC times are only associated with evidence. Each operation records: API inbound / basic validation end → claim submitted → host takeover → compilation / evidence gathering / encoding complete → prepare/authorize/consume start-end → consume success reply → first socket write → provider first byte / first content → AppendOutput committed ACK → first-chunk delivery → last provider content → tail-chunk ACK → settle committed → terminal-state delivery. Permit added latency is measured from API inbound to the consume success reply, avoiding measuring only the final CAS; the authorize and final consume spans are listed separately. If evidence-gathering network / credential resolution happens before the permit, it too counts in this full chain and is listed separately; added latency must not be claimed as meeting the target by excluding slow steps.

Total business latency, provider response / generation time, and ANT per-stage times are presented separately. First-chunk added latency is measured from the provider's first content entering the decoder to the persistent ACK/delivery; tail latency from the last content to the persistent terminal state/delivery. Do not derive the ANT p95 by subtracting the provider p95 from the overall p95; pair the spans per request first, then compute quantiles. Rejections without a permit are recorded as submission-to-stable-rejection and are not mixed into the successful-permit p95/p99; timed-out / unconverged operations get their own counts and observation cutoff states, and samples must not be dropped.

| Measurement group | Method and observations | Behavioral assertions |
|---|---|---|
| Normal streams, concurrent long streams | Record stream speed and bytes, chunk trigger reason, wait times, batch sizes, ACK latency, writer queue depth / control queue, lock waits, CPU/RSS/goroutines, and per-stream / total buffer high-water marks | Ordering per stream, bodies persisted before visible; memory bounded by the frozen active count and budget; throughput and rejection classification explicit |
| Slow consumers / not reading at all / browser disconnect | Local controlled consumers pause or throttle while the production rate is kept; record detach triggers, buffering and continued background saving, and reconnect backfill reading | Thresholds such as 30s serve as assertions only after IN-05 freezes them; subscription exit does not mean business cancellation or external termination |
| Slow DB, batch rollbacks, writer saturation | Controlled storage delay/failure while keeping the source stream supplied; measure the blockage propagating from AppendOutput to decoder/network, ACK tail latency, and control responses | The fixed buffer must not grow unboundedly; uncommitted chunks are not delivered; cancel/settle/heartbeat capability is retained; timeouts have explicit failure/unknown |
| Body reaching the limit / response idle | Test samples above and below the boundary based on the frozen 16MiB/idle candidates; record retention length, the partial flag, local stop, and external proof | Retention does not exceed the frozen cap; results state the retrieval scope; without termination evidence the real reservation cannot be released |
| 2-hour sustained run and the convergence tail | Sample reservations/active/uncertain/encumbrance, connections, tasks, queues, and goroutines periodically; after the run, verify item by item within the frozen convergence budget | Legitimate unknowns listed separately; residues that are known-terminated and should have been released, ownerless sustained tasks, and unbounded buffers all fail; "passing" by wiping data is not acceptable |

Control-queue priority and backpressure behavior should be verified in the fault / limit groups; frozen values do not guarantee correctness. The preparation environment must not turn off durable writes, reduce the historical volume, relax idle, or shrink outputs to pass and then pass the results off as production metrics; if a separate scenario baseline is truly needed, record the new version and its scope of applicability before measurement, and keep the original targets and failure results.
