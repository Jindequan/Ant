## 1. Recommended Deployment and Identity Boundaries (IN-02, D02/D07)

A resident Go server, an independently built Web, and a single SQLite Store using the existing modernc/database/sql implementation are recommended. The server and database sit on the same host's local persistent disk; only one business server instance is deployed, with a single writer, a bounded write queue, and a limited number of read-only connections. SQLite must not be placed on a cross-machine shared disk, and quota must not be shared across multiple instances each with its own SQLite. It is recommended that Web and API be served through the same entry point, reducing browser identity and deployment complexity.

The target OS has not been obtained, and the current development machine must not be treated as a deployment fact. If the target is Linux, a dedicated non-root system user + resident systemd with failure restart is recommended; if the user selects containers, use a single replica + a local persistent volume with a guaranteed stop grace period, still exactly one Store, never delivering two deployments at the same time. IN-02 has the executor verify the target host OS/architecture/access method, disk persistence, process manager, and the compatibility of the Go/Web build tooling with the accepted lockfiles, then select the single installation path. systemd/containers are alternative operations approaches; neither is currently installed or verified.

The business process is recommended to listen only on the loopback address; if the public network is needed, proxy through an HTTPS entry point on the same machine; if the target is local-only use, use the local entry point. Whether to open access to other devices/the public network depends on the real callers; user count or network scope must not be inferred from "single host". The management interface and metrics require management authorization, and pprof is off by default; during testing, only a controlled management listener (existing design 05 §5). For deployment directories, code/data separation is recommended, with the data directory at 0700 and the master key file at 0600 (permissions come from design 05 §5); paths are settled after confirmation on the target host, and the database/master key must not enter source directories or logs.

The identity scheme carries over design 05 §5: the administrator bootstraps once via the local CLI, and the server side stores only hashes for session/API tokens; no public registration. Browsers are recommended to use server-managed sessions, and external calling programs rotatable API tokens, with grants limited to namespace, pool, and execute/manage permissions. The namespace is derived from the AuthProvider and server-side grants, and the request body cannot be trusted (design 03 §2). The specific users/administrators/calling programs and the sources of their permissions are unverified; token validity periods and browser session cookie/CSRF details are to be proposed and verified by AUTH-01, and this file must not claim the implementation already exists.

Secrets carry over AES-GCM, a fresh random nonce per entry, and ref+revision as associated data, with the master key kept outside the database. Credential bodies only enter approved secret sources/encrypted storage interfaces, and documents record only ref/revision/mask; the Transport holds plaintext temporarily, and the Adapter and logs never touch it. Key rotation produces a new revision; after an old revision is revoked, the final pre-send guard rejects it, while calls already sent continue to settle under the old plan. Backup data and the master key are managed separately; actual account read/test permissions and billing authorization have not yet been obtained.

## 2. Initial Parameters and Their Sources (IN-04 and IN-05)

All of the following are candidates. The original design's initial values are reused directly, without claiming they already satisfy real AI scenarios. Freeze order: real deployment/provider facts → load and measurement definitions → fault and resource budget verification → acceptance by the responsible roles. The user does not need to design algorithms one by one or approve ordinary technical values.

| Parameter | Candidate value | Source and rationale / verification points |
|---|---:|---|
| maxActiveOperations | 128 | design 05 §1 initial value; this is the global host ceiling, and actual admission is still limited by verified account concurrency; it can be lowered once real memory and provider concurrency are determined |
| writerQueue / control reserve | 512 / 128 | design 05 §1; control and settlement must not be starved by body floods; freeze after confirming the actual queue-implementation meaning of the reserved capacity |
| readConnections | 4 | design 05 §1; single-host read-parallelism starting point; verify it does not widen writer contention |
| lease / heartbeat / sweep | 30s / 10s / 5s | design 05 §1; heartbeat shorter than lease, sweep period bounded; verify dispatch latency/database busyness and lost lease renewals; no promise that unknown reservations are released within 5s |
| planningMaxRounds | 3 | design 03 §3, design 05 §1; bounds candidate replanning; not equal to the number of outbound calls |
| commandBudget / SQLite busy | 50ms / 10ms | design 05 §1; starting points for short-transaction budget and lock waits, to be measured on the actual driver/queue; the budget must not masquerade as a p95 metric |
| sweep batch | 100 | design 03 §7; contend on owner/generation conditions to avoid unbounded sweep transactions |
| cancel/control batch / poll | 100 / 1s | design 05 §4; the supervisor reads persistent state on a fixed cycle so lost notifications remain visible; a fallback is retained even for a single process |
| stream chunk | 32KiB or 50ms | design 05 §3; chunk by whichever threshold is hit first, avoiding one transaction per token; first-chunk latency must be measured for real |
| per-stream ring | 128KiB | design 05 §3; bounded buffer backpressure when the database is slow; unbounded accumulation is not allowed |
| saved body ceiling | 16MiB / operation | design 05 §3 initial body limit; under different encodings it is explicitly counted in persisted bytes and includes all attempts, preventing circumvention across attempts (the counting scope is a supplement from this proposal, to be accepted) |
| response idle / consumer idle | 30s each | design 05 §3; recommended to distinguish provider read idleness from slow subscription consumption; a slow browser must not trigger provider retries |
| writer output batch | 32 items / 256KiB / 25ms | design 05 §3; batching across attempts, per-item guards, whole-batch rollback on failure; control takes priority; no promise of latency below the batch wait |
| default maxAttempts | 1 | new engineering candidate: outbound calls are not automatically added when failure safety is unproven; it can be raised later after a verified retry whitelist and budget; fixed at the first claim |
| default deadline | 120s | new engineering candidate: a conservative limit for the thinnest AI text test; not applicable to unverified long-reasoning/tool tasks; frozen after real model latency and user flows are obtained |
| graceful stop budget | 30s | new engineering candidate: same order of magnitude as the initial lease, giving bounded time for stop admission, fact commits, and resource convergence; not proof of external completion |
| settlement/recovery context | 5s per invocation, no more than 30s total, at most 3 ledger replays | new engineering candidate: independent of business cancellation, using the original attempt/reportId/receipt; brief storage faults get a bounded recovery opportunity and the provider is never retried; accepted after LED/OPS verify the actual writer cancellation and commit boundaries |

128 fully loaded streams alone take about 16MiB of ring budget; saving a full 16MiB body per operation means about 2GiB of persisted bodies if 128 operations are at the limit simultaneously. This is a budget computed from candidate ceilings, not measured traffic or memory usage, and it does not yet include decoders/tasks/indexes/WAL/logs. Real model response sizes, peak concurrency, disk write rates, and available space have not been obtained. IN-04 should freeze peak concurrency/commit rates/typical and maximum request-response sizes/latency percentiles/endurance duration, and specify the measurement environment; D04 must not be closed on this table alone.

## 3. D06 Lifecycle, Failure, and Recovery Behavior

Status note (2026-10-04): the ledger-side behaviors in the table below (cancel intent, granted revocation, reliable unsent settlement, conservative unknown, sweep takeover and generation guards, late reports appended only) were implemented and independently accepted in the G1-DEV six-leaf local SQLite synthetic batches (`docs/evidence/WORK/G1-DEV/INDEPENDENT-REVIEW.md`); after LED-03 it was reopened because usage exceeding int64 cannot retain the original values as designed, and current results do not cover that path, see `docs/evidence/WORK/LED-03/REOPENING-REVIEW.md`. The "exits pending verification" in this table refer to verification against real drivers, cross-process fault injection, and provider boundaries, still executed per the original milestones (T2.2 fault acceptance/T3); the D06 parameters themselves remain unfrozen.

Clock uses an injected server-side clock; time is taken uniformly inside the ledger writer, so database conditions, leases, and deadlines share one time definition (design 03/05). The target host is recommended to enable reliable system time synchronization and record time anomalies; once rollback is detected, close new permits and keep settlement of already-sent facts, and quota must not be increased by rolling time back. Specific anomaly detection thresholds and recovery actions must be determined by D06 fault cases; do not fill in a fake threshold without clock evidence.

| Trigger | Existing behavior definitively adopted | Exit pending verification |
|---|---|---|
| Browser close/SSE disconnect | Only detach the subscription; the operation ctx is created by the supervisor, not derived from r.Context; saving and settlement continue within the limit | Same-ID queries and the events cursor resume reading persisted chunks; the provider's original stream is not resumed and no new call is issued |
| Slow browser | Detach once consumer idle is reached; do not block other subscriptions or cancel the provider; reconnection reads from persisted data | A two-client + slow-consumer case proving the body is persisted before it becomes visible |
| Queue full/database slow | Bounded queueing, control priority, backpressure to the network within the ring; explicit failure/unknown after timeout | Output must not be silently dropped or commits fabricated; record the persistence failure and query the commit result by the original receipt |
| User cancel/deadline/provider idle | Persist the cancellation/reason, the supervisor stops local I/O; facts settle first; already-successful reports go through the unified resolver | timeout/EOF/5xx/cancel are none of them proof of unsent or finished; do not stitch by switching providers |
| Unauthorized attempt/prepared | Close the attempt and release the reservation only with reliable unsent facts | Race against the authorize/consume CAS; one side commits and the other does not apply partial resource changes |
| granted but not consumed | Atomic revoked; release unexecuted resources; already-granted budget is not returned | Verify against the design 03 §9 AbortBeforeDispatch matrix |
| consumed with reliable unsent proof | Settle as not_executed once same-source proof for the original permit/attempt passes | Ordinary call parameters cannot be trusted; bounded replanning is allowed only when all policy guards are satisfied |
| consumed but send/completion unclear | unknown; count at the verified upper bound, occupancy active→uncertain, open the corresponding encumbrance/hold | Automatic resend is forbidden; lease expiry/service restart/cross-day reset must not release unknown external reservations |
| heartbeat lost/process crash | After lease expiry, bounded sweeping per phase/permit state; generation increments, unconsumed permits are revoked, and the old owner can no longer obtain new permits/consumption eligibility | The sweep must not take over resending; a pause after consume succeeded but before the socket write can still allow one late send; a late owner only appends evidence and does not overwrite stable final states |
| Late report/verification completion | The original unknown final state is retained and reconciliation appends evidence; Adjustment records the real difference, and reliable completion proof releases the corresponding encumbrance | Prevent duplicate adjustments/releases; queries show both the original result and the subsequent accounting confirmation |
| System clock rollback | Close new permits; already-sent calls keep being accounted | Verified by fault injection; recovery requires normal time and reliable guards; uncertainty must not be released by directly calling clearHold |

Recommended normal shutdown order: stop accepting new Submits/new permits while keeping queries and settlement; close unsent paths per the unified abort matrix, send local cancellation to in-flight requests and save the facts already obtained; converge best-effort with an independent bounded settlement ctx. Calls still lacking completion proof when the grace period expires at exit keep unknown/encumbrance; if a storage fault prevents persisted settlement, record the fault explicitly, and after restart lease sweeping and receipt queries recover; do not claim that exit means refund. The process manager's stop timeout must exceed the application's candidate grace period and include exit margin; concrete values are set after the target OS and manager are confirmed.

The final send boundary carries over design 03 §4/A20: pausing until expiry before the final consume check guarantees zero sends; a pause after consume succeeds but before the socket write can still allow one late send, and without provider fencing absolute withdrawal cannot be claimed. Therefore lease/generation revocation cannot substitute for external completion evidence, and the sweep must conservatively keep unknown reservations and never take over resending.

After a crash, startup is recommended to first run restore/database integrity and schema checks, initialize the supervisor, and handle expired owners per the existing recovery rules before opening new admission. Distinguish ordinary restarts from backup restores: restoring an old backup must set restore_guard, check backup gaps and unknown calls, and open only after an audited management authorization (design 05 §5); it does not automatically clear old operations or increase capacity.

The Transport carries over the accepted single-request guardrails: billed non-empty POSTs, GetBody=nil, HTTP/1.1, SDK automatic retries/redirects forbidden; billed GETs/empty-body probes use a separate single-use connection. HTTP/2 is not enabled until it passes replay verification. A lost consume reply is only queried/converged, never resent; the test server must count the requests actually received (design 05 §2). These are design requirements; real candidate adapters are not yet implemented/verified.

## 4. D05 Persistence, Cleanup, and Backpressure Recommendations

The first version is recommended to persist bodies by default, to honor queries/replays after browser disconnects; SSE is published only after the body chunk append and visible_output_at succeed in the same transaction, and events reference chunk ranges (design 05 §3). When the body limit is reached, record partial/the limit reason, stop local reads, and keep the reservation if there is no external completion proof. The retrievable range and the unretrievable truncated portion must be clearly expressed; content must not be shown first and then disappear due to a write failure, and metadataOnly results must not be described as fully recoverable.

**Retention candidate: bodies for 7 days, with explicit administrator-initiated body deletion supported.** The 7 days is a new data-retention recommendation from this proposal, giving a reviewable starting point between the recovery window and storage cost; with no real user requirements or disk statistics, it is not a frozen value. Cleanup deletes only body chunks allowed to expire and leaves a cleaned state/time; it does not delete dedup identities, operation/attempt results, accounting events, unknowns and their verification evidence (the latter is explicitly never auto-deleted by design 05 §5). The body retention period/whether metadataOnly is allowed involves user-data tradeoffs and requires the necessary ruling; users are not asked to design cleanup algorithms. Logs contain no bodies, credentials, or secret headers, and are structurally correlated by operation/attempt/account/binding/pool/offer/config.

**Backup candidate: a daily consistent SQLite snapshot, keeping the most recent 7 copies, with the master key backed up independently.** The frequency and copy count are new operations recommendations arising from single-host failure recovery needs; RPO/RTO and backup targets have not been obtained, and zero data loss cannot be claimed. First clarify the backup destination/disk space/encryption and access permissions, then measure-verify restoration into a separate directory: restore_guard stays closed to outbound calls while checking the recoverability of configuration, pools, the ledger, events, occupancy, and keys. Never copy a single file of the live database directly while ignoring the WAL.

**Backpressure details pending convergence are resolved by the executor:** whether a single provider's idle includes persistence backpressure time, the wait deadline after the ring fills, control-command priority and allocation fairness, the critical condition between the total body budget and available disk, and error classification for settlement replays. It is recommended that idle evaluate only the phase waiting for new provider data, with database waits counted separately in the persistence budget, so normal backpressure is not misdiagnosed as a stuck provider; specific thresholds must be frozen after real backlog measurements. Every anomaly must persist a visible reason or be explicitly not persisted; normal final states must not be used to mask storage faults.

## 5. Acceptance Criteria and the Minimal Facts to Obtain

The technical proposal is completed and verified by the executor and accepted by the original roles; the user only supplies the real boundaries and the necessary permission/cost/data-retention choices. Current gaps: the actual calling application and a minimal sanitized request, target host OS/access clues, real accounts/plans and approved credential sources for the two candidates, permitted real test actions and cost ceilings, and body-retention tradeoffs. There are three candidates in total, and it is not assumed that all three must be implemented; IN-03 selects two admissible providers based on evidence.

| Given / When | Then (later acceptance evidence) |
|---|---|
| The same operation completes after a browser disconnect, then a reconnecting query | Reads the same-ID persisted result and chunks, without one extra provider request |
| Cancel, exit, and crash at each of the prepared/granted/consumed stages | Check real request counts, permit states, resource sets, and the next prepare against the design 03 matrix; return codes are not accepted as self-proof |
| Slow database, full queue, slow consumer, body at its limit | Buffers stay bounded at all times, control commands can advance, committed output is replayable, and failure and partial/unknown reasons are genuinely visible |
| Lease expiry or clock rollback, late old owner | The old owner has no new permits/consumption eligibility; a pause after verification can still allow one late send, unknown reservations do not vanish, and late facts are appended only during verification |
| Backup restore/credential revocation/cross-namespace requests | restore_guard closes first, permissions are finally decided server-side, and old-credential permits are rejected; no historical balance rollback or external resending |
| Two real bundles sanitized and mapped to the accepted Compile | The actual zero-issue artifacts match the verified types/windows/scopes/upper bounds/initial snapshots; missing facts are explicitly inadmissible |
